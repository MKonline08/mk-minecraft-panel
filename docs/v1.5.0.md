# v1.5.0 — Confirmed startup repairs and installed-mod search

Mods/Plugins now has a separate installed-file search, an All/Enabled/Disabled filter, matching counts, and Clear search. It filters locally by filename without modifying any files.

## Diagnosis and confirmation

Open Mods/Plugins → Startup diagnosis & repair → Diagnose startup. The panel reads up to the last 4 MiB of logs/latest.log and indexes enabled JAR hashes and mod IDs. Explicit mod blame in deferred-task failures or mandatory-dependency errors can produce a disable trial. If Modrinth identifies the exact installed JAR and resolves a compatible release, the panel also proposes an exact replacement and necessary dependency changes. The Particle Effects config-loading crash is one supported explicit-blame pattern.

Choose one proposal and confirm the displayed file changes. Diagnosis alone never modifies installed files. Plans are bound to the server, runtime, and enabled-file inventory; changed files require a new diagnosis. Candidates retain the Minecraft/loader versions. Unknown JARs, incompatible dependencies, duplicate projects, unavailable upstream metadata, and ambiguous failures can prevent an update proposal. Latest compatible metadata does not prove a bug is fixed. Client mod versions may need matching changes.

Confirmed repairs stop Minecraft, make a verified backup, preserve a full recovery copy, apply the selected changes, and test startup health and RCON. A failed test restores the original server files and leaves Minecraft stopped; the error, test log, and backup name remain visible. Successful repairs retain Roll back repair until Keep this repair is chosen while stopped. Backups still follow retention. Keep enough free space for the live server, complete rollback copy and archive.

Interrupted file changes or verification block startup until repair rollback. Repair recovery copies are stored in staging and records in panel.sqlite. Files retained during rollback remain available for diagnosis. Runtime metadata is restored with rollback. The previous Modrinth-managed-file manifest is cleared when a repair changes its JAR set; future repair identification uses exact content hashes.

The panel does not promise to repair every modpack, damaged world, configuration problem, machine/network issue, or unsupported custom runtime. Where no definitive single mod is identified, it shows log evidence and requests manual review instead of guessing. No mods are silently changed in the background.

## Startup controls

Stop in Overview can now interrupt an active startup-readiness check. It remains guarded during file-changing stages. Startup checks fail promptly when the container restarts, surfacing crash/restart loops instead of waiting the full twenty minutes. Cancelling a repair verification rolls the attempted repair back.

## Validation and upgrade

Tests cover diagnosis, candidate updates, stale-plan rejection, explicit confirmation, successful repair/rollback, failed-test recovery, interrupted recovery, and installed-file filtering on desktop/mobile. The live Fabric/Forge/NeoForge pack tests additionally disable a real mod under explicit fixture confirmation, verify readiness, roll back, and restart the restored pack. CI gates release on the existing eight-runtime matrix, packaged checks, and upgrades from populated v1.2.1, v1.3.0 and v1.4.1 installations.

After release, stop Minecraft and back up the complete CasaOS data directory. Change only the existing panel image to ghcr.io/mkonline08/mk-minecraft-panel:1.5.0; preserve host ports, HOST_DATA_DIR and the data mount.
